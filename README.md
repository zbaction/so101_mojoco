# SO-101 桌面抓取场景 (MuJoCo)

桌面抓取场景，包含 SO-101 六轴机械臂、三色方块、目标收纳盒，以及场景相机与腕部相机。
另附一个**六状态自主抓取-放置状态机**：不依赖人工干预，机器人自己把方块夹起来放进收纳盒。
规划所用的方块与收纳盒坐标来自**场景相机的 RGB 图像**（`vision.py`），不读仿真真值。

## 快速开始

```bash
cd ~/so101_mujoco
source .venv/bin/activate

python view_scene.py            # 打开交互式 MuJoCo 查看器
python capture_cameras.py       # 把两个相机渲染成 scene_cam.png / wrist_cam.png
ARM_POSE=grasp python capture_cameras.py    # 在抓取姿态下渲染

python pick_place.py                     # 视觉引导抓取+放置（默认绿色方块）
python pick_place.py --cube red          # 换红色方块
python pick_place.py --viewer            # 边跑边看（按真实时间播放）
python pick_place.py --frames out/       # 每个状态导出一张 PNG
python pick_place.py --no-vision         # 关掉视觉，改用仿真真值规划（对照用）
python pick_place.py --cameras           # 边跑边开两个实时相机窗口（全景 + 腕部）

python vision_demo.py                    # 渲染一帧，把识别结果画在图上存成 vision_demo.png

python stack_cubes.py                    # 三个方块叠成一座塔（见下）
python stack_cubes.py --viewer           # 看这座塔
python stack_cubes.py --cameras          # 两个相机窗口里看这座塔

python pick_any.py                       # 从摞里把方块逐个夹进收纳盒（见下）
python pick_any.py --cube green          # 只把指定颜色放进盒子，其余搬到一边
```

## 场景内容

- **桌面**：0.6 × 0.6 m 木纹台面，台面位于世界坐标 `z = 0`，中心 `(0.18, 0, 0)`。
- **方块**：边长 20 mm、质量 20 g、`condim=4`（带扭转摩擦，便于夹取）。
  - `cube_red`   `(0.200, -0.120)`
  - `cube_green` `(0.235, -0.045)`
  - `cube_blue`  `(0.215,  0.030)`
- **收纳盒** `bin`：130 × 130 mm、内壁高 35 mm，中心 `(0.215, 0.135)`，内部有 `bin_center` 站点。
- **场景相机** `scene_cam`：`pos="0.5360 -0.3660 0.4110"`，`fovy="40"`，俯视整个工作区。
- **腕部相机** `wrist_cam`：装在 `wrist_camera` body 上（镜头面外移 23.5 mm），光轴沿手指方向，`fovy="62"`。

> ⚠️ **`fovy` 的单位永远是度**，不受 `<compiler angle="radian"/>` 影响。写成 `0.65` 会得到 0.65° 的视场，画面几乎全空。

## 机械臂

6 个位置执行器（`class="sts3215"`，`kp=998.22`、`kv=2.731`）：

```
shoulder_pan  shoulder_lift  elbow_flex  wrist_flex  wrist_roll  gripper
```

工作空间实测（以 `gripperframe` 站点为 TCP，垂直向下抓取姿态）：

- 可达范围主要落在 `x ≈ 0.14–0.30`、`y ≈ ±0.15`、`z < 0.09`（世界坐标）；
- `z > 0.10` 时姿态可达性急剧变差，`x > 0.30` 基本无法竖直抓取；
- 夹爪命令 `gripper ≈ 0.2–0.5` 时开口约 24–29 mm，适合夹 20 mm 方块。

已验证的抓取姿态（绿色方块，TCP 误差 < 2 mm）：

```
shoulder_pan 0.215, shoulder_lift 0.179, elbow_flex 0.107, wrist_flex 1.284, wrist_roll 0.264
```

## 视觉感知 (`vision.py`)

不装 OpenCV，只用 numpy / scipy / mujoco。场景相机是**针孔模型**：`F = (H/2) / tan(fovy/2)`，
1280×960 下 `F = 1318.8 px`，于是「像素 ↔ 世界平面」可以双向换算。

### 怎么从一张 RGB 图得到 6 个数字

**方块 (x, y, yaw)**：方块是已知的 20 mm 立方体躺在 `z = 0.0102` 的平面上，所以三自由度就完全
决定了它的剪影。做法是把模型的 8 个角点按 `(x, y, yaw)` 投影、取凸包，与观测到的颜色掩膜算
**精确多边形 IoU**（Sutherland-Hodgman 裁剪，不做光栅化、不用梯度），再对这个 IoU 做粗扫 + Nelder-Mead。
`yaw` 折叠到 `[0, π/2)`——正方形转 90° 不变，正好是平行夹爪所需的对称性。

**收纳盒 (x, y)**：不能取剪影质心。相机只看到盒子的一侧墙，可见面积不是中心对称的，质心反投影
**偏 12.8–14.5 mm**。改成拟合已知的 130×130×35 mm 开口盒模型，误差降到 **0.6 mm**。

**必须先求「桌面 ROI」再做颜色分割**。不加位置约束时，**蓝天（hue 228、sat 0.83、val 0.78）会被
当成蓝方块**——原始掩膜 84739 px，而真方块只有 646 px。桌面靠木纹色（hue 12–52、sat > 0.25、
val > 0.12）形态学取最大连通域得到。

### 精度（20 个随机摆位 × 3 色 = 60 样本，0 漏检）

| 分辨率 | 位置误差 mean / max | 偏航误差 mean / max | IoU mean / min |
| --- | --- | --- | --- |
| **1280×960（采用）** | **0.47 / 0.94 mm** | **1.06 / 2.83°** | **0.982 / 0.955** |
| 640×480 | 0.93 / 1.67 mm | 2.53 / 8.45° | 0.960 / 0.896 |

分辨率就是精度：640×480 下方块只有约 55 px 宽，撑不起 1° 的偏航。**所以感知固定用 1280×960**，
与 `scene_cam` 的 `resolution` 属性无关（渲染尺寸由 `mujoco.Renderer` 决定）。

### 耗时

1280×960 下（VM 负载会漂，给区间而不是点值）：

| 操作 | 耗时 |
| --- | --- |
| 单帧渲染（含方向护栏） | 50–90 ms |
| `find_cube`（单色） | 230–350 ms |
| `find_bin` | 155–300 ms |
| `find_all_cubes` + `find_bin`（三色全量，仅 demo 用） | 400–640 ms |

一次完整抓放只在两个时刻看图（出发前看方块、搬运前看盒子），所以视觉总开销约 **0.5–0.7 s**，
对 3 s 的抓放流程是可接受的；纯 headless 跑完整流程墙钟约 0.1 s。

两个把「看起来该很贵」的部分做掉的优化，都验证过**结果逐位相同**：

- **轮廓提取**：原本把整块剪影的 50 491 个像素全喂给 `hull2d`，**161 ms**。但连通区域的凸包
  一定由「每行最左/最右像素 + 每列最上/最下像素」撑起来，四次 `argmax` 取极值点只要 **1.2 ms**，
  再求凸包 **0.8 ms**，得到的凸包与暴力法**顶点数、面积、坐标完全一致**（18 个随机摆位 A/B：
  xy 差 0.000000 mm、yaw 差 0.000000°、IoU 差 0.000000）。
- **方向护栏降采样**：判断画面是否上下镜像只需一个木色质心，用 1/4 分辨率算 HSV
  （85 ms → 3.9 ms），质心从 upright 631 / 镜像 329 两组参考值照样分得开。

### 跟控制器怎么接

`pick_place.py` 只把视觉用于**规划**，状态完成判据仍然全部读物理：

| 环节 | 数据来源 |
| --- | --- |
| 夹哪个方块、往哪儿走、夹爪绕哪个角度闭合 | `vision.Perception.find_cube()` |
| 放到哪里 | `vision.Perception.find_bin()` |
| 状态是否完成、方块是否真的被抬起、是否落进盒子 | 仿真（关节角、接触、方块位置） |

这样分工的好处是：识别错了会表现为「抓空 / 抓偏」，而不是「状态机自认为成功」。

- 每次尝试开始时重新看一次方块；下降途中方块被碰位移超过 2.5 mm 会重新看图并重新瞄准。
- 一帧没认出来会重试（`VISION_RETRIES = 3`）；**仍然认不出来就抛 `VisionError`，该次尝试作废**，
  绝不悄悄退回仿真真值——否则"识别失败"和"识别成功"在日志里长得一模一样。
- `--no-vision` 时视觉完全不参与，规划直接读仿真（用于对照实验）。

### 实测

30 个随机摆位（`x ∈ [0.170, 0.260]`、`y ∈ [-0.100, 0.020]`、随机偏航，三色轮流）：

```
30/30 通过   视觉误差 mean 0.31 mm / max 0.62 mm   仿真耗时 mean 3.07 s / max 3.34 s
```

标称摆位三色全 PASS（`--cube red|green|blue`），视觉误差 0.24–0.31 mm、盒子 0.61 mm。

### 环境坑（WSLg）

1. **同一个进程里不要同时存在两个 `mujoco.Renderer`。** 实测：在已有一个 renderer 的情况下再建一个，
   读回的画面会坏——每隔一帧返回的是**精确的上下镜像**（`|f − prev[::-1]| = 0.00`），亮度均值也会
   从 107 漂到 137。用单 renderer 连渲 200 帧则**一帧不坏**（桌面 IoU 恒为 0.451）。
   所以 `PickPlace(..., perception=per)` 支持传入共享的 `Perception`，批量跑多轮时复用它。
2. 新建 GL 上下文的第一帧偶尔是近黑的（mean ≈ 15，正常 107）。`Perception.__init__` 会先空渲一帧，
   `render()` 见到偏暗的帧会自动重渲。
3. `mujoco.Renderer(model, height, width)` 的参数顺序是「高, 宽」，写反了不会报错，只会得到一张
   尺寸不对的图。

## 自主抓取-放置 (`pick_place.py`)

### 六个状态

| 状态 | 动作 | 完成条件 |
| --- | --- | --- |
| `MOVE_ABOVE` | 张开夹爪移到方块正上方 65 mm | 关节到达目标并稳定 0.15 s |
| `DESCEND` | 下降：高处全速，最后 3 cm 慢速 | 关节到达目标，或方块被手指碰位移超过 2.5 mm（自动重新瞄准） |
| `CLOSE` | 闭合夹爪 | 夹爪被物体顶住（指令与实际差 > 0.05 rad 持续 40 ms）或到机械限位 |
| `LIFT` | 垂直抬起 | 关节到达目标（夹爪只比较**指令**，见下） |
| `MOVE_TO_BIN` | 水平搬到收纳盒上方 | 关节到达目标（同上） |
| `OPEN` | 张开夹爪放下 | 张到 0.22 rad 以上、方块已落回低处且**速度归零** |

若 `LIFT` 结束后方块没有真的离开桌面（高度上升 < 30 mm），会带着 ±4 mm 的横向偏移重试，最多 3 次。

### 几何要点（这两个数不对就一定抓空）

1. **`PINCH_OFFSET = 0.013`**：手指真正的捏合点不在 `gripperframe` 站点原点上，而在站点 **+z 轴前方 13 mm** 处。所以 IK 的目标必须是「方块中心往回退 13 mm」，否则手指伸出去旁边夹空气。
2. **`GRASP_SITE_Z = 0.010`**：站点必须降到**方块中心高度**。手指尖在站点下方约 7 mm，站点若停在方块顶面（z≈0.02），夹爪闭合的是方块上方的空气。

另外，抓取时会让夹爪的闭合轴跟随**方块的偏航角**（`cube_yaw()`，按 90° 折叠）。始终沿世界 +X 闭合时，方块一旦转过 45° 左右，两个手指就只顶到对角，方块会被挤出去——这是随机位置测试里唯一的失败模式。
接了视觉之后这个角度直接取自图像（`Pose.yaw`），不再需要从仿真读。

### 实测结果

```
python pick_place.py --cube red      RESULT: PASS   峰值 71.6 mm  落点误差 8.4 mm
python pick_place.py --cube green    RESULT: PASS   峰值 70.5 mm  落点误差 9.1 mm
python pick_place.py --cube blue     RESULT: PASS   峰值 71.8 mm  落点误差 9.3 mm
```

随机位置鲁棒性测试：

- **纯视觉引导**（30 个随机摆位）：**30/30 通过**，视觉误差 mean 0.29 mm，落点误差平均 6.8 mm。
- 仿真真值引导（60 个随机摆位，`--no-vision`）：**60/60 通过**，落点误差平均 7.4 mm、最大 8.3 mm（收纳盒半宽 62 mm）。

> 注意：方块之间如果贴得太近（间距 < 25 mm），抬起时会把相邻方块一起带起来，这属于场景摆放问题，不是控制器问题。

### 一次完整抓放的耗时

仿真时间和真实时间几乎 1:1（2 ms 步长，物理计算每步不到 0.02 ms）：

| 状态 | 仿真耗时 |
| --- | --- |
| `MOVE_ABOVE` | 0.40 s |
| `DESCEND` | 0.39 s |
| `CLOSE` | 0.25 s |
| `LIFT` | 0.11 s |
| `MOVE_TO_BIN` | 0.43 s |
| `OPEN` | 0.89 s |
| **合计** | **≈ 2.5 s** |

加上两次看图（约 0.7 s），视觉版单次抓放仿真耗时 **≈ 3.1 s**。`--viewer` 模式下墙钟约 5–11 s（视觉推理是纯 CPU 的，会额外占用真实时间）；纯 headless 模式整个流程只要 **0.1 s**（不等真实时间）。

### 实现要点

- **IK**：阻尼最小二乘 + `mj_jacSite`，同时约束位置与姿态（approach 沿世界 −Z，夹爪闭合轴沿方块偏航角），多随机种子重试，单次求解 1–2 ms。
- **运动**：关节参考以 4.0 rad/s 斜坡推进，夹爪 1.6 rad/s，避免瞬跳造成冲击。
- **状态完成判据**：与实际关节角度比较**最终目标**（不是移动中的参考），否则状态会在第一帧就误判完成。
- **抓取确认**：靠「夹爪指令领先实际 > 0.05 rad 且持续 40 ms」判断顶到物体，而不是只看接触对数量（接触会瞬时出现又消失）。

#### 降低延迟时踩过的三个坑

1. **拿夹着方块的夹爪去比"实际角度 = 指令角度"**。方块顶住手指时实际角度永远追不上指令，`LIFT` 完成后会一直等夹爪慢慢滑到容差内——这就是"抬起来然后卡住好几秒"的直接原因。搬运动作改为只比较**夹爪指令**是否到位。
2. **状态机没有"卡住"判据**。手指压在方块上、手腕顶到桌面时，关节误差会停在一个固定值上永远不动，状态机只能干等。现在有看门狗：0.3 s 内误差改善不到 0.002 rad 就判定受阻，直接进入下一状态。
3. **`OPEN` 用固定 1.2 s 定时**。改成「张到 0.22 rad 且方块落地并静止」后既更快又更稳。

顺带两个数据上的发现：

- 快速张开夹爪会把方块**弹飞 13 mm**，所以释放动作单独用 0.45 rad/s，比抓取动作慢。
- 下降途中手指会蹭到方块。加了「方块位移 > 2.5 mm 就重新瞄准」后，下降不再把方块推走。

## 三个方块叠成一摞 (`stack_cubes.py`)

`scene.xml` 里红/绿/蓝三个方块是平铺在桌面上的。这个脚本生成一份布局相同、但把三个方块**竖直叠成一座塔**的场景
（`mjcf/scene_stack.xml`），机械臂、桌面、收纳盒、两个相机都保持不变。

```bash
python stack_cubes.py --rebuild          # 从 scene.xml 重新生成 mjcf/scene_stack.xml
python stack_cubes.py                    # 落定 2 s 后打印每块的高度与层间距
python stack_cubes.py --viewer           # 交互式看这座塔
python stack_cubes.py --cameras          # 两个实时相机窗口
python stack_cubes.py --save out/        # 导出 scene_cam / wrist_cam 两张 1280x960 PNG
```

叠放参数（脚本顶部常量，改这里比改 XML 安全）：

| 常量 | 值 | 说明 |
| --- | --- | --- |
| `TOWER_XY` | `(0.215, -0.045)` | 塔的位置，就是原来绿方块所在处 |
| `STACK` | `("red","green","blue")` | 自下而上 |
| `BOTTOM_Z` | `0.0102` | 最底层方块的中心高度（方块半高 10 mm，桌面 z=0） |
| `CUBE_HEIGHT` | `0.020` | 方块边长，也是层间距 |

每块留 `0.0002 m` 的初始间隙，避免求解器从互相嵌入开始；三块各带一点点互不相同的偏航（0.10 / −0.06 / 0.22 rad），
看起来像手叠的而不是 CAD 对齐的。

### 实测

```
stack: red -> green -> blue (bottom -> top)
  red    ( 0.2150, -0.0450,  0.0100) m
  green  ( 0.2150, -0.0450,  0.0300) m
  blue   ( 0.2150, -0.0450,  0.0500) m
  level spacing: 19.99, 20.00 mm
  tower height: 59.8 mm (top face at z = 0.060 m)
  STACK_INTACT
```

放在那里跑 10 s 仿真，三层中心相对初始位置漂移分别 0.22 / 0.43 / 0.63 mm，层间距始终保持 20 mm，塔不塌。

> 这只是**场景布局**。`pick_place.py` 抓的是桌面上自由躺着的方块；从一摞里夹任意一块（含中层/底层）由
> `pick_any.py` 负责，见下一节。

## 从一摞里夹任意方块 (`pick_any.py`)

`stack_cubes.py` 把三块叠成一摞之后，`pick_place.py` 只会抓桌面上自由躺着的方块——从摞里直接抽中层或底层会把整摞撞翻。
`pick_any.py` 专门做这个任务，而且**不是把所有方块都丢进收纳盒**：它对每块做一次决策。

```bash
python pick_any.py                 # 全部搬进收纳盒（清塔）
python pick_any.py --cube red      # 只把红色放进盒子；蓝、绿搬到桌面旁边
python pick_any.py --cube green    # 只把绿色放进盒子；蓝搬到桌面旁边
python pick_any.py --cube blue     # 蓝色本来就在塔顶：直接放进盒子
python pick_any.py --viewer        # 边跑边看
python pick_any.py --cameras       # 两个实时相机窗口
python pick_any.py --frames out/   # 每个阶段存一张 scene_cam PNG
```

### 机器人的决策：要的那块进盒，挡路的搬到一边

塔是按顺序叠的，要拿中间/底下那块，必须先把它上面的清走。但“清走”不等于“丢进盒子”。所以每抓起一块塔顶方块时，机器人判断：

- **它就是你要的那块**（或你没指定 `--cube`）→ 放进**收纳盒**；若是目标，本轮即结束；
- **它不是你要的那块**（只是压在目标上面）→ **搬到桌面旁边的停车位**（塔两侧各一个，`(0.180,-0.115)` 与 `(0.250,-0.115)`），不碰收纳盒。

于是 `--cube red` 的结果是：蓝、绿被放在桌上，**只有红色进盒**。停车位离塔和盒子都 >55 mm，
IK 在 0.010 / 0.030 / 0.065 三个高度都是 0.00 mm 误差（`PickPlace` 为此新增了 `drop_xy` 参数：为 `None` 时进盒，给定 `(x,y)` 时放到桌面的指定点）。

### 为什么必须从塔顶往下一个一个来

平行夹爪只能从上方下探。中层/底层的方块被上面的压着，手掌（`geom 27`，60×65×144 mm）在下探时会先撞到上层，
把整摞推倒——直接抓中层/底层会把塔撞翻。所以中间/底下的方块，只有先把上面的搬走（搬到停车位）、让它变成塔顶，才能抓。
“夹任何一个”＝“点名任意一块，先把它上面的搬到一边，再夹它”。

### 视觉怎么知道该抓哪一块、抓多高

`vision.find_all_cubes_3d()` 一帧里给每块一个 `(x, y, yaw, z)`。被上层压住的方块 z 拟合并不可靠，
但**塔顶那块永远完全可见**，所以每轮只取“还在塔上、z 最高”的那块当塔顶，它的 z 是可信的。
实测塔顶蓝块 z=0.046（真值 0.050），再**吸附到最近的 20 mm 层高**（0.010 / 0.030 / 0.050）得到抓取高度，
拟合偏置就被这条物理先验抹平了。

识别里还有一处关键：`find_cube` 现在接受 `centre_z`，用**已知抓取高度**做反投影。
否则把塔顶的方块当成“贴着桌面”来反投影，x、y 会偏出几十毫米（实测 49.7 mm），直接把机械臂引到空气里。

### 高度是逐块参数化的

原来的抓取/搬运/释放高度是模块常量（只适合桌面上的单块）。现在 `PickPlace` 接受
`grasp_z / carry_z / release_z / lift_rise`，默认值与原行为逐位相同。每抓一块前按实测层高传参：

| 参数 | 塔顶层 | 中层 | 底层 |
|---|---|---|---|
| `grasp_z`（夹爪停靠点高度） | 0.050 | 0.030 | 0.010 |
| `carry_z`（搬运高度） | 0.070 | 0.065 | 0.065 |
| `lift_rise`（算作抬起的抬升量） | 0.015 | 0.030 | 0.030 |

`carry_z` 封顶 0.075：更高的搬运高度在收纳盒上方 IK 解不准（0.080 → 1.41 mm，0.085 → 3.92 mm）。

### 下探高度这个坑（决定了成败）

接近高度（`pregrasp_z`）最初沿用“能到达的最高点”0.092 m。但塔顶抓取时这个高度让机械臂伸到几乎极限，
IK 解有约 1 mm / 1° 的残差，**那 1° 的倾斜让手掌边缘啃进塔顶方块，把方块顶偏**（日志里 `cube nudged 2.6 mm aside` 反复出现）。
抓取高度 0.044–0.052 的扫描显示：0.092 封顶时塔顶方块被顶下塔，0.080 封顶时每次都稳稳夹起并进盒。
所以 `pregrasp_z = min(grasp_z + 0.065, 0.080)`。

### 实测

```
$ python pick_any.py --cube red
pick 1: cube_blue  decision: NOT the target (red wanted) -> PARK aside at (0.180, -0.115)
pick 2: cube_green decision: NOT the target (red wanted) -> PARK aside at (0.250, -0.115)
pick 3: cube_red   decision: this is the target -> put it IN THE BIN
SUMMARY
  cube_blue   PARKED on table (3 mm from its slot)
  cube_green  PARKED on table (7 mm from its slot)
  cube_red    xy-to-bin   6.7 mm  IN BIN
RESULT: PASS - only cube_red is in the bin; cube_blue, cube_green parked on the table.
```

其它场景：`--cube green`（蓝被停到一边、绿进盒）、`--cube blue`（蓝色直接在塔顶、进盒）都 PASS；
不带 `--cube` 时退回“整摞清进盒子”的老行为（三块全部 IN BIN）。`--viewer` 下同样 PASS。

### 每抓一块之间会回一次“家”

抓完一块后机械臂停在收纳盒上方。若直接从盒子上方规划下一块的接近姿态，关节插值可能扫过塔。所以每抓一块之间
用 `retract()` 把关节插值回初始的 home 姿态（走的是同一套限速跟踪器，纯关节空间，不会扫过塔），再开始下一块。

## 实时相机窗口 (`camera_windows.py`)

运行时弹出两个窗口，左边 `scene_cam`（全景），右边 `wrist_cam`（腕部），画面左下角叠一行状态与仿真时间。
抓放过程中窗口会随状态机实时刷新（`MOVE_ABOVE` → … → `OPEN`），随时按 `Esc` 或关闭窗口即可停止。

```bash
python pick_place.py --cameras                  # 跟着抓放流程实时显示
python pick_place.py --cameras --no-shadows      # 画面略平，但刷新率约翻倍
python camera_windows.py                         # 只看空场景，不跑抓放
python camera_windows.py --save out/             # 顺便把最后显示的一帧存成 PNG
```

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `--camera-size` | `640x480` | 每个窗口的像素尺寸 |
| `--camera-fps` | `12` | 刷新率上限 |
| `--camera-budget` | `0.60` | 窗口最多占用多少比例的真实时间用于绘制 |
| `--no-shadows` | 关 | 跳过阴影 pass，绘制开销约降到 1/3 |

### 为什么要单独一个 renderer

`mujoco.Renderer` 的尺寸在构造时固定、**没有 resize**（`width`/`height` 是只读属性）。视觉模块自己持有一个 1280×960 的 renderer，
如果拿它来显示，就得每帧渲染 1280×960 再丢掉 3/4 的像素；所以显示另开一个小 renderer（640×480），两个相机共用这一个。

实测（本机 WSLg 软件渲染，两个相机各渲一帧为一对）：

| 配置 | 一对的耗时 |
| --- | --- |
| 两路 1280×960 | 135 ms |
| 两路 640×480 | 70 ms |
| 两路 640×480，关阴影 | 25 ms |
| 两路 512×384，关阴影 | 47 ms |

### 为什么要给绘制限流

这是本次改动里唯一真正反直觉的地方。三件事都是实测出来的：

1. **不能按仿真时间刷新**。最初用 `viewer_period = 1/60 s`（仿真时间）触发重绘，于是 3.08 s 的动作用了 **10.24 s** 真实时间——每对画面 65 ms，
   3 s 里要刷 185 次。改成按真实时间的 fps 上限节流后才回到 1:1。
2. **不能"落后就不画"**。改成"落后于时钟就跳过这一帧"之后，`--viewer` 同时开着时 `viewer.sync()` 让程序永久处于落后状态，
   3 s 只画出 **2 帧**，窗口看起来像卡死。
3. **必须给绘制一个时间预算**。最终做法是双闸门：`--camera-fps` 限制刷新率，`--camera-budget` 限制窗口占总真实时间的比例（默认 60%）。
   预算超了就跳过这一帧，物理计算从不等待显示。

实测（绿色方块，3.08 s 动作，两路 640×480）：

| 预算 | 画出帧数 | 实际帧率 | 墙钟 / 仿真 |
| --- | --- | --- | --- |
| 0.40 | 17 | 5.3 fps | 1.04 |
| 0.60 | 21 | 6.4 fps | 1.07 |
| 0.60（512×384） | 23 | 7.2 fps | 1.03 |

对照：纯 headless 是 0.57（比真实时间快，不等时间），只开 `--viewer` 是 1.16。也就是说窗口打开后整场抓放仍然接近实时播放。

### 坏帧防护

和视觉模块同一个坑：WSLg 下读回的帧偶尔是**上下镜像**的。窗口这一路用两种判据兜底：

- 绝对判据（仅 `scene_cam`）：木色桌面必须落在画面下半部分；
- 相对判据：若这一帧和上一帧**倒过来**更像，就翻回来（首帧用"同一状态连渲两次互相比对"来定标）。

判据在半分辨率上跑（2 ms 而不是 10 ms），因为两个候选行相差数百像素，降到一半分辨率不影响结论。

### 已知问题（环境相关）

WSLg + GLFW 下 `--viewer` 退出时进程会以段错误结束（X Error `BadDrawable`），这是 WSLg 的老问题，不影响抓取结果，退出码也不受影响（`pick_place.py` 结果本身正常）。
`--viewer` 与 `--cameras` 同时开时会多一个 GL 上下文，退出时同样会报 `GLXBadDrawable` / `double free`，抓放结果依旧正确，只是收尾不干净。

另：`PIL.ImageGrab.grab(xdisplay=":0")` 在这个 WSLg 会话里无法截取整个 X 屏幕（`X get_image failed`），所以窗口画面是否正常只能靠图像统计指标来核对。
因此 `camera_windows.py --save DIR` 保存的是**送进窗口的那一张图**（含左下角状态文字），可直接用来确认显示内容。
